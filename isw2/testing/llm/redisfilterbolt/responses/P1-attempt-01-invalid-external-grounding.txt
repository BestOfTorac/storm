Di seguito trovi prima l’analisi test-oriented della classe, poi la progettazione di esattamente 11 test e infine una suite Java completa con esattamente 11 metodi annotati con@Test. La soluzione evita Redis reale, rete e attese, isolando il bolt tramite Mockito e una piccola sottoclasse di test.

1. Analisi di RedisFilterBolt
1.1 Scopo della classe

RedisFilterBolt è un bolt Storm che:

estrae una chiave dal Tuple tramite RedisFilterMapper;
interroga Redis usando un comando dipendente dal tipo configurato;
inoltra il tuple sullo stream predefinito quando l’elemento esiste;
conferma sempre il tuple con ack quando l’elaborazione termina normalmente;
in caso di eccezione, segnala l’errore e marca il tuple come fallito.

La documentazione della classe dichiara il supporto per:

STRING
HASH
SET
SORTED_SET
HYPER_LOG_LOG
GEO

Il pom.xml mette a disposizione Java 25, JUnit Jupiter, Mockito e gli artefatti Storm 3.0.0, incluso storm-redis. Non è quindi necessario aggiungere dipendenze per la suite proposta.

Validazione significativa

Il costruttore basato su JedisPoolConfig verifica che, per il tipo SET, additionalKey non sia null. In caso contrario genera:

Java
1
new IllegalArgumentException("additionalKey should be defined")
Mostra più linee

Questa è una condizione facilmente testabile con un oracle preciso.

La stessa validazione non compare nel costruttore basato su JedisClusterConfig. Questa asimmetria è osservabile, ma non viene usata come test principale perché potrebbe essere un’omissione accidentale e non una funzionalità intenzionale.

Input significativi dei costruttori
tipo Redis restituito dal mapper;
additionalKey presente;
additionalKey == null, in particolare con SET;
mapper o descrizione null.

Gli ultimi due casi genererebbero verosimilmente una NullPointerException, ma il codice non dichiara una politica esplicita per input null. Testarli avrebbe quindi un valore funzionale inferiore rispetto alla validazione esplicita per SET.

Fase 3: controllo dipendente dal tipo

1.4 Comportamenti osservabili e oracle
Quando found == true

Il bolt esegue:

Java
1
collector.emit(input, input.getValues());
2
collector.ack(input);
Mostra più linee

Gli oracle principali sono quindi:

viene emesso il contenuto completo del tuple;
il tuple originale viene usato come anchor;
viene chiamato ack(input);
non vengono chiamati fail(input) o reportError(...).
Quando found == false

Il bolt non emette nulla, ma esegue comunque:

Java
1
collector.ack(input);
2
``
Mostra più linee

Gli oracle sono:

nessuna emissione;
un acknowledge;
nessun fallimento.
Quando si verifica un’eccezione

Il blocco catch esegue:

Java
1

2
collector.fail(input);

Non viene effettuato ack. L’eccezione non viene propagata al chiamante.

1.6 Dipendenze da mockare
RedisFilterMapper

È opportuno mockarlo perché controlla:

il tipo Redis;
l’eventuale additional key;
la chiave estratta dal tuple;
la dichiarazione dei campi di output.
JedisCommandsContainer

Deve essere mockato perché rappresenta l’accesso a Redis. Usare un server Redis reale trasformerebbe i test in integration test, introducendo stato esterno, configurazione, rete e potenziale non determinismo.

OutputCollector

Va mockato per osservare:

emit;
ack;
fail;
reportError.
Tuple

Va mockato perché nei test è sufficiente controllare:

il riferimento passato al mapper;
i valori restituiti da getValues().
OutputFieldsDeclarer

Va mockato per verificare la delega di declareOutputFields.

1.7 Funzionalità difficili o meno adatte a uno unit test

Non è opportuno verificare in questa suite:

la connessione reale a Redis;
il funzionamento interno di Jedis;
pool, cluster, autenticazione, timeout o failover;
la serializzazione Storm del bolt;
l’esecuzione del bolt dentro una topologia reale;
la semantica reale dei comandi Redis sui vari tipi di dato.

Questi aspetti richiederebbero integration test separati.

Inoltre, nel codice fornito non è presente l’implementazione di AbstractRedisBolt. La strategia di test assume, coerentemente con l’API Storm, che getInstance() sia protected e che collector sia accessibile alle sottoclassi. L’API documentata di AbstractRedisBolt espone precisamente questi elementi.

Osservazione tecnica

La variabile jedisCommand viene ottenuta tramite getInstance(), ma process non mostra una chiamata di restituzione o rilascio dell’istanza. Non è però corretto costruire un test che imponga un rilascio, perché tale comportamento non è presente nella classe fornita e non è possibile dedurre se JedisCommandsContainer lo richieda in questa versione.

2. Progettazione degli 11 test
Test 1: SET senza additional key
Funzionalità: validazione del costruttore con pool.
Scenario: tipo SET, additionalKey == null.
Risultato atteso: IllegalArgumentException con messaggio "additionalKey should be defined".
Test 2: STRING esistente
Funzionalità: filtro di una chiave Redis.
Scenario: exists(key) restituisce true.
Risultato atteso: emissione dei valori del tuple e ack.
Test 3: STRING inesistente
Funzionalità: eliminazione di un tuple non corrispondente.
Scenario: exists(key) restituisce false.
Risultato atteso: nessuna emissione, ma ack.
Test 4: SET contenente il valore
Funzionalità: controllo di appartenenza a un set.
Scenario: sismember(additionalKey, key) restituisce true.
Risultato atteso: uso corretto di additional key e chiave, emissione e ack.
Test 5: HASH contenente il campo
Funzionalità: controllo dell’esistenza di un campo hash.
Scenario: hexists(additionalKey, key) restituisce true.
Risultato atteso: emissione e ack.
Test 6: SORTED_SET con rank zero
Funzionalità: controllo di appartenenza a un sorted set.
Scenario: zrank restituisce 0L.
Risultato atteso: il tuple viene considerato trovato, emesso e confermato.
Test 7: HYPER_LOG_LOG con conteggio zero
Funzionalità: controllo del conteggio HyperLogLog.
Scenario: pfcount(key) restituisce 0L.
Risultato atteso: nessuna emissione, ma ack.
Test 8: GEO con lista vuota
Funzionalità: gestione di un risultato geografico senza posizione.
Scenario: geopos restituisce una lista vuota.
Risultato atteso: nessuna emissione, ma ack.
Test 9: GEO con almeno una coordinata non null
Funzionalità: riconoscimento di una posizione geografica esistente.
Scenario: la lista contiene un elemento null e una coordinata valida.
Risultato atteso: emissione e ack.
Test 10: eccezione del comando Redis
Funzionalità: gestione degli errori.
Scenario: il comando Redis genera una RuntimeException.
Risultato atteso: reportError, fail, nessun ack e nessuna emissione.
Test 11: dichiarazione dei campi
Funzionalità: dichiarazione dello schema di output.
Scenario: chiamata a declareOutputFields.
Risultato atteso: delega al mapper con lo stesso declarer.

Controllo finale della suite

La suite contiene esattamente:

11 metodi annotati con @Test;
1 test di validazione del costruttore;
test per tutti e 6 i tipi Redis supportati;
rami sia positivi sia negativi;
un test di gestione delle eccezioni;
un test di delega per declareOutputFields;
nessuna connessione a Redis;
nessuno sleep;
nessun accesso di rete;
nessuna modifica al codice di produzione.
Scelte di miglioramento

La suite usa una sottoclasse esclusivamente per creare un seam controllabile attorno a getInstance() e al collector. In questo modo i test verificano i comportamenti funzionali del bolt, mentre Mockito viene limitato alle dipendenze esterne e agli oggetti Storm che non è utile costruire concretamente.
