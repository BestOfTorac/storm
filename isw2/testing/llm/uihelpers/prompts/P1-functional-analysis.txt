## Output richiesto

Organizza la risposta ESATTAMENTE nelle otto sezioni seguenti.

### 1. Responsabilità pubbliche della classe

Descrivi le principali responsabilità funzionali osservabili di UIHelpers.

Non limitarti a un elenco meccanico dei metodi: quando più metodi fanno parte
della stessa responsabilità funzionale, evidenzialo.

### 2. Inventario delle funzionalità pubbliche testabili

Produci una tabella con una riga per ogni metodo o funzionalità pubblica
rilevante.

Per ogni riga indica:

- nome del metodo/funzionalità;
- ruolo funzionale;
- principali input;
- output o effetto osservabile;
- collaboratori o dipendenze;
- eventuale configurazione/stato coinvolto;
- difficoltà qualitativa di test:
  semplice, media oppure difficile;
- breve motivazione della difficoltà.

Non proporre casi di test concreti.

### 3. Classi di input e condizioni significative

Individua le categorie di input funzionalmente significative osservabili dal
codice di produzione.

Considera, soltanto quando applicabili:

- valori normali;
- null;
- stringhe vuote/non vuote;
- stringhe valide/malformate;
- collezioni vuote/non vuote;
- configurazioni presenti/assenti;
- identificatori validi/non validi;
- valori limite;
- combinazioni funzionalmente differenti.

Non trasformare queste categorie in test numerati.

### 4. Comportamenti osservabili e possibili oracle

Per ogni grande area funzionale indica quali risultati o effetti potrebbero
essere osservati in un futuro test.

Esempi possibili, solo se pertinenti al codice:

- valore restituito;
- contenuto di una struttura dati;
- header o risposta prodotta;
- eccezione osservabile;
- interazione con un collaboratore;
- configurazione di un oggetto prodotto;
- stato osservabile dopo l'operazione.

Non scrivere assertion Java.

Non proporre ancora casi di test.

### 5. Collaboratori e dipendenze

Distingui esplicitamente:

A. collaboratori utilizzabili direttamente in unit test;
B. collaboratori che potrebbero richiedere mocking;
C. infrastruttura che sarebbe preferibile evitare in unit test;
D. funzionalità che sembrano richiedere integration test.

Per ogni elemento spiega brevemente la motivazione.

### 6. Rischi di testabilità

Analizza eventuali difficoltà dovute, quando presenti, a:

- stato globale;
- metodi statici;
- framework esterni;
- filesystem;
- rete;
- HTTP;
- Jetty;
- configurazioni complesse;
- oggetti difficili da istanziare;
- concorrenza;
- timing;
- dipendenze esterne.

Non proporre modifiche al codice di produzione per rendere i test più facili.

### 7. Confini dell'esperimento

Indica quali responsabilità o funzionalità sembrano ragionevolmente adatte a
futuri unit test deterministici.

Indica separatamente quali sembrano inappropriate, troppo costose o fragili
per una suite unitaria generata dall'LLM.

Motiva ogni esclusione sul piano funzionale o tecnico.

### 8. Incertezze

Elenca esclusivamente gli aspetti che NON puoi determinare con sicurezza dai
file di produzione forniti.

Per ciascuno specifica:

- cosa non è determinabile;
- perché il contesto corrente è insufficiente;
- quale ulteriore classe, file o informazione di PRODUZIONE servirebbe.

Non chiedere test esistenti o risultati sperimentali.
