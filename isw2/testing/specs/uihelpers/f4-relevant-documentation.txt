   50: The UI and logviewer processes provide a way to not only see what a cluster is
   51: doing, but also manipulate running topologies.  In general these processes should
   52: not be exposed except to users of the cluster.
   53:
   54: Some form of Authentication is typically required, and can be done using a java servlet filter
   55:
   56: ```yaml
   57: ui.filter: "filter.class"
   58: ui.filter.params: "param1":"value1"
   59: logviewer.filter: "filter.class"
   60: logviewer.filter.params: "param1":"value1"
   61: ```
   62:
   63: The `ui.filter` is an instance of `javax.servlet.Filter` that is intended to
   64: filter all incoming requests to the UI and authenticate the request mapping
   65: it to a "user".  Typically this is done by modifying or wrapping the
   66: `HttpServletRequest` to return the user principal through the
   67: `getUserPrincipal()` method or returning the user name through the
   68: `getRemoteUser()` method.  If your filter authenticates in a different way you
   69: can look at setting `ui.http.creds.plugin` to point to an instance of `IHttpCredentialsPlugin`
   70: that can take the `HttpServletRequest` and return a user name and populate the needed fields
   71: in the current `ReqContext`.  These are advanced features and you may want to look at the
   72: `DefaultHttpCredentialsPlugin` as an example of how to do this.
   73:
   74: These same settings apply to the logviewer too.  If you want to have separate control
   75: over how authentication works in the logviewer you may optionally set `logviewer.filter`
   76: instead and it will override any `ui.filter` settings for the logviewer process.
   77:
   78: If the cluster is single tenant you might want to just restrict access to the UI/log

  322:
  323: ### CSRF Protection
  324:
  325: The Storm UI REST API does not currently include built-in Cross-Site Request Forgery (CSRF) protection. State-mutating endpoints can potentially be triggered by a malicious website if a user has an active authenticated session in the same browser. This is particularly relevant when using browser-based authentication mechanisms such as Kerberos (SPNEGO), as the browser automatically attaches credentials to cross-origin requests.
  326:
  327: To mitigate this risk, configure your reverse proxy to enforce CSRF token validation or same-origin checks on POST requests.
  328:
  329: ### Security Response Headers
  330:
  331: The Storm UI does not set security-related HTTP response headers by default. Operators deploying a secured cluster should configure the following headers via their reverse proxy or a custom servlet filter configured through `ui.filter`:
  332:
  333: - `X-Frame-Options: DENY` or `SAMEORIGIN` to prevent clickjacking attacks
  334: - `X-Content-Type-Options: nosniff` to prevent MIME type sniffing

   24: ## REST API Base URL
   25:
   26: The REST API is part of the UI daemon of Storm (started by `storm ui`) and thus runs on the same host and port as the
   27: Storm UI (the UI daemon is often run on the same host as the Nimbus daemon).  The port is configured by `ui.port`,
   28: which is set to `8080` by default (see [defaults.yaml](conf/defaults.yaml)).
   29:
   30: The API base URL would thus be:
   31:
   32:     http://<ui-host>:<ui-port>/api/v1/...
   33:
   34: You can use a tool such as `curl` to talk to the REST API:
   35:
   36:     # Request the cluster configuration.
   37:     # Note: We assume ui.port is configured to the default value of 8080.
   38:     $ curl http://<ui-host>:8080/api/v1/cluster/configuration
