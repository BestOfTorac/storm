    7: ### Generic Resources
    8: Generic Resources allow Storm to reference arbitrary resource types. Generic Resources may be considered an extension of the resources enumerated by the [Resource Aware Scheduler](Resource_Aware_Scheduler_overview.html), which accounts for CPU and memory.
    9:
   10: ### API Overview
   11: For a Storm Topology, the user can now specify the amount of generic resources a topology component (i.e. Spout or Bolt) is required to run a single instance of the component. The user can specify the resource requirement for a topology component by using the following API call.
   12: ```
   13:    public T addResource(String resourceName, Number resourceValue)
   14: ```
   15: Parameters:
   16: -   resourceName ??? The name of the generic resource
   17: -   resourceValue ??? The amount of the generic resource
   18:
   19: Example of Usage:
   20: ```
   21:    SpoutDeclarer s1 = builder.setSpout("word", new TestWordSpout(), 10);
   22:    s1.addResouce("gpu.count", 1.0);
   23: ```
   24:
   25: ### Specifying Generic Cluster Resources
   26:
   27: A storm administrator can specify node resource availability by modifying the _conf/storm.yaml_ file located in the storm home directory of that node.
   28: ```
   29:    supervisor.resources.map: {[type<String>] : [amount<Double>]}
   30: ```
   31: Example of Usage:
   32: ```
   33:    supervisor.resources.map: {"gpu.count" : 2.0}
   34: ```

  192:
  193: ## Topology Priorities and Per User Resource
  194:
  195: The Resource Aware Scheduler or RAS also has multi-tenant capabilities since many Storm users typically share a Storm cluster.  Resource Aware Scheduler can allocate resources on a per user basis.  Each user can be guaranteed a certain amount of resources to run his or her topologies and the Resource Aware Scheduler will meet those guarantees when possible.  When the Storm cluster has extra free resources, Resource Aware Scheduler will to be able allocate additional resources to user in a fair manner. The importance of topologies can also vary.  Topologies can be used for actual production or just experimentation, thus Resource Aware Scheduler will take into account the importance of a topology when determining the order in which to schedule topologies or when to evict topologies
  196:
  197: <div id='Setup'/>
  198:
  199: ### Setup
  200:
  201: The resource guarantees of a user can be specified *conf/user-resource-pools.yaml*.  Specify the resource guarantees of a user in the following format:
  202: ```
  203:     resource.aware.scheduler.user.pools:
  204: 	[UserId]
  205: 		cpu: [Amount of Guarantee CPU Resources]
  206: 		memory: [Amount of Guarantee Memory Resources]
  207: ```
  208: An example of what *user-resource-pools.yaml* can look like:
  209: ```
  210:     resource.aware.scheduler.user.pools:
  211:         jerry:
  212:             cpu: 1000
  213:             memory: 8192.0
  214:         derek:
  215:             cpu: 10000.0
  216:             memory: 32768
  217:         bobby:
  218:             cpu: 5000.0
  219:             memory: 16384.0
  220: ```

  280:
  281: We currently use a slightly different approach. We simulate scheduling the highest priority topology for each user and score the topology for each of the resources using the formula
  282:
  283: ```
  284: (Requested + Assigned - Guaranteed)/Available
  285: ```
  286:
  287: Where
  288:
  289:  * `Requested` is the resource requested by this topology (or a approximation of it for complex requests like shared memory)
  290:  * `Assigned` is the resources already assigned by the simulation.
  291:  * `Guaranteed` is the resource guarantee for this user
  292:  * `Available` is the amount of that resource currently available in the cluster.
  293:
  294: This gives a score that is negative for guaranteed requests and a score that is positive for requests that are not within the guarantee.
  295:
  296: To combine different resources the maximum of all the individual resource scores is used.  This guarantees that if a user would go over a guarantee for a single resource it would not be offset by being under guarantee on any other resources.
  297:
  298: For Example:
  299:
  300: Assume we have to schedule the following topologies.
  301:
  302: |ID|User|CPU|Memory|Priority|
  303: |---|----|---|------|-------|
  304: |A-1|A|100|1,000|1|
  305: |A-2|A|100|1,000|10|
